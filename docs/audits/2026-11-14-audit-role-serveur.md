# Audit du rôle Serveur (14 novembre 2026)

## Ce que le serveur doit pouvoir faire

Décisions écrites du propriétaire (9 novembre 2026) : le serveur prend les commandes à la caisse et les fait avancer. Il ne fait **aucune** opération d'argent (paiement, remboursement, offert, ardoise, code promo, annulation de ticket).

Permissions par défaut du rôle `waiter` : voir la carte, voir et gérer les commandes, utiliser la caisse. Pas d'encaissement, pas de rapports, pas d'inventaire, pas d'équipe, pas de paramètres.

## Méthode

Base de démonstration locale, plusieurs personnes connectées **en même temps** dans des navigateurs séparés (serveur, chef, caissier, propriétaire), pour vérifier que l'information circule entre les pôles. Chaque étape est vérifiée à l'écran ET dans la base.

## Le parcours de service testé de bout en bout

| Étape                                                        | Qui      | Résultat                                                                                   |
| ------------------------------------------------------------ | -------- | ------------------------------------------------------------------------------------------ |
| 1. Prendre une commande à la caisse pour une table           | Serveur  | OK : la commande est créée, rattachée au serveur et à la table, la table passe « occupée » |
| 2. La commande arrive en cuisine sans recharger              | Chef     | **Corrigé** : avant, 12 à 15 s (aucun événement temps réel reçu). Après : 1 s              |
| 3. Préparer puis marquer prête                               | Chef     | OK : « DÉMARRER » puis « TERMINER », statut « prête » en base                              |
| 4. La commande prête apparaît chez le serveur sans recharger | Serveur  | OK après correction du temps réel (compteur « Commandes » mis à jour en direct)            |
| 5. Marquer servie (« Livré »)                                | Serveur  | OK : statut « livrée », heure de service enregistrée, paiement laissé « en attente »       |
| 6. Retrouver la commande pour l'encaisser                    | Caissier | OK                                                                                         |

## Accès du serveur

- Refusés comme prévu (renvoi vers « accès refusé ») : Inventaire, Fiches techniques, Fournisseurs, Historique du stock, Rapports, Factures, Journal d'audit, Équipe, Paramètres, Permissions, Abonnement, Ardoises, Coupons, Publicités.
- Ouverts par conception (écrans opérationnels, actions de modification masquées sans permission) : Tableau de bord, Commandes, Caisse, Service, Cuisine, Cartes, Catégories, Plats, QR codes.
- Argent : pas de bouton d'encaissement à la caisse ni dans le détail d'une commande, chiffre du jour et ticket moyen masqués sur le tableau de bord.

## Décisions du propriétaire, livrées

Les quatre réponses du propriétaire (14 novembre 2026) sont appliquées et vérifiées dans le navigateur, avec deux serveurs, un chef et le propriétaire connectés en même temps. Chaque mesure a un témoin qui doit répondre « non ».

| Décision                                               | Ce qui a été fait                                                                                                                                                                                                           | Vérification                                                                             |
| ------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| 1. Son et vibration quand une commande est prête       | Sur n'importe quel écran ouvert : son, vibration et message « Commande prête - Table X ». Application fermée : notification push. Seuls préviennent le serveur qui a pris la commande et celui à qui la table est attribuée | Serveur 1 : message en 1 s, vibration, son joué. Serveur 2 (témoin, pas sa table) : rien |
| 2. Table rattachée au serveur qui prend la commande    | À la caisse, une commande sur place d'un serveur lui attribue la table si personne ne l'a encore                                                                                                                            | Après la commande : 1 attribution active, au nom du serveur 1                            |
| 3. Carte « Total des revenus » masquée pour le serveur | Masquée pour tout rôle sans accès aux rapports                                                                                                                                                                              | Serveur : 0 carte. Propriétaire (témoin) : 1 carte                                       |
| 4. Table obligatoire pour une commande sur place       | La caisse refuse l'envoi en cuisine et affiche « Choisissez la table »                                                                                                                                                      | Message visible, 0 commande créée                                                        |

Limite connue, écrite dans le code : l'attribution automatique n'est pas atomique. Deux serveurs qui commandent pour la même table libre à la même seconde peuvent tous deux être attribués. Un index unique n'est pas la bonne réponse : l'attribution manuelle laisse déjà plusieurs serveurs actifs sur une table (les écrans affichent le plus récent), donc le pire cas de cette course est un état que l'application gère déjà.

## Relecture indépendante

Un second agent a relu tout le travail. Il n'a trouvé aucune fuite de données entre restaurants. Ses 8 remarques sont toutes corrigées et couvertes par un test qui échoue si la correction est retirée :

1. La règle « table obligatoire » bloquait les restaurants sans table configurée : elle ne s'applique plus que s'il existe des tables.
2. L'alerte sonnait de nouveau quand on modifiait une commande déjà prête après un rechargement : seule une vraie transition vers « prête » déclenche l'alerte.
3. Deux appuis sur « prête » envoyaient deux notifications : seul un vrai changement de statut en envoie une.
4. La notification push vibre, sonne de nouveau et reste affichée jusqu'à ce que le serveur la touche.
5. Chaque commande prête faisait relire les attributions par tout le personnel : relecture seulement lors d'une vraie transition, et seulement quand la table n'est pas déjà connue comme la sienne. (Les attributions de table ne sont pas publiées « en direct », d'où cette relecture.)
6. Une erreur de lecture des attributions comptait comme « table libre » : elle bloque maintenant l'attribution automatique.
7. Une erreur au démarrage de l'envoi de la notification ne pouvait pas être journalisée : elle l'est.
8. Tests manquants sur le branchement de l'action cuisine et de la route caisse : ajoutés.

Vérifié sur une version de production locale, deux serveurs connectés : le serveur qui a pris la commande reçoit message, son et vibration ; le collègue rien ; une commande QR sur une table attribuée **après** l'ouverture de l'écran alerte bien son serveur ; modifier une commande déjà prête après rechargement ne sonne pas ; la renvoyer en cuisine puis la remettre prête sonne de nouveau.

## Note sur la méthode de test

En développement, Next recopie chaque message du navigateur dans un fichier journal, et cette écriture provoque un rechargement de la page, donc un nouveau message : la page se recharge en boucle. C'est propre à l'environnement de développement (mesuré : 0 rechargement parasite sur la version de production). Les vérifications d'écran ont donc été faites sur une version de production locale, et l'envoi des commandes de caisse par l'API en développement, parce qu'en production locale la limitation de débit bloque par conception les requêtes sans serveur Redis.
